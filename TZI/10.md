# 10. Distribuované a paralelní souborové systémy, NFS a GFS

## Distribuované souborové systémy (DFS)
* **Charakteristika:** Souborový systém, kde klienti, servery a úložná zařízení jsou rozptýleny na různých uzlech sítě. Uživateli se však systém jeví jako jeden lokální souborový systém.
* **Cíle:** Transparentnost (lokace, přístupu), sdílení dat, odolnost proti výpadkům, škálovatelnost.

### Souborový systém NFS (Network File System)
* **Popis:** Vyvinut společností Sun Microsystems. Umožňuje připojit (mount) vzdálený adresář ze serveru do lokálního stromu souborů klienta.
* **Implementace:** 
  * Funguje na architektuře Klient-Server.
  * Komunikace probíhá typicky přes RPC (Remote Procedure Call).
  * Tradičně je NFS server **bezstavový (stateless)** – neudržuje si informace o otevřených souborech jednotlivých klientů, což usnadňuje zotavení po výpadku. (Novější NFSv4 stavové prvky přidává).
* **Základní operace:** Vytvoření souboru, čtení, zápis, odstranění, získání atributů.
* **Komponentní operace (Složené operace v NFSv4):**
  * Protokol NFSv4 zavedl "Compound operations". 
  * Namísto posílání mnoha drobných RPC dotazů (např. otevři, přečti, zavři), pošle klient jeden složený (komponentní) dotaz, který obsahuje více operací. Server je postupně vyhodnotí. 
  * Výrazně se tím snižuje režie a latence na síti.

## Paralelní souborové systémy
* **Charakteristika:** Navrženy pro vysoce výkonné počítání (HPC). Data souboru nejsou na jednom disku/serveru, ale jsou "rozprostřena" (striping) napříč více úložnými uzly.
* **Výhoda:** Klienti mohou číst/zapisovat části jednoho obrovského souboru *současně z mnoha serverů* paralelně, čímž se násobí propustnost.

### Google File System (GFS)
* **Popis:** Distribuovaný a paralelní souborový systém vyvinutý Googlem pro obrovské objemy dat. Optimalizován pro dávkové čtení a sekvenční zápis (append), běží na levném (commodity) hardwaru, kde se počítá s častými výpadky uzlů.
* **Architektura:**
  * **Master node (Řídící uzel):** Udržuje metadata (adresářovou strukturu, mapování souborů na bloky). Obvykle jen jeden pro jednoduchost.
  * **Chunkservers (Datové uzly):** Ukládají samotná data. Soubory jsou rozděleny na **chunky** (typicky 64 MB). Každý chunk je replikován (běžně 3x) na různé chunkservery.
* **Algoritmus pro čtení:**
  1. Klient se zeptá Mastera, kde (na kterém chunkserveru) se nachází požadovaný chunk.
  2. Master vrátí seznam chunkserverů s replikami.
  3. Klient si vybere nejbližší/nejrychlejší chunkserver a přímo od něj data přečte. (Data nejdou přes Mastera!).
* **Algoritmus pro zápis (Append):**
  1. Klient získá od Mastera lokace replik chunku. Jedna z replik je určena jako **Primary (Primární)**.
  2. Klient pošle data všem replikám najednou (data jsou uložena v bufferu chunkserverů).
  3. Klient řekne Primární replice: "Proveď zápis".
  4. Primární replika určí přesné pořadí zápisu, aplikuje ho lokálně a přikáže ostatním replikám provést zápis ve *stejném pořadí*.
  5. Po potvrzení od všech replik ohlásí Primární replika úspěch klientovi.
